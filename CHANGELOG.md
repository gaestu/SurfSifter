# Changelog

All notable changes to this project will be documented in this file.

## Unreleased

- Fixed **Chromium Session Restore** and **Chromium Cache** not finding files on other partitions when many browsers are selected (about seven or more). For Chromium Session Restore this included the default selection of all browsers: a session file on a second partition was never extracted, and the run ended with `ok` and no note; the default selection of Chromium Cache was not affected. The file list query had more path patterns than SQLite accepts in one query (1,800 for sessions and 2,016 for the cache with all 14 browsers; SQLite accepts just under 1,000). The error was not written to the evidence log, to `manifest.json` or to `processing.log`, only to the console, and the extractor went on as if the file list had no match. The query is now split into several queries of at most 850 patterns, for every extractor that uses the file list, so the number of browsers or patterns can no longer make it fail. Selections that worked before give the same result; those of up to 850 patterns, such as the default selection of Chromium Cache, still run as one query. A failed file list query is now written to `processing.log` for every extractor. If the query fails for another reason, Chromium Session Restore and Chromium Cache now stop with status `error`, with the reason in the evidence log and in `manifest.json`, instead of searching only the open partition. A resumed Chromium Cache run keeps its partial manifest so that it can still be continued; the reason is then only in the evidence log. A run that stopped this way is not reused by **Run All**, and **Ingest Results** shows the reason instead of a completed ingestion with zero records. Chromium Session Restore still handles an error in the check whether a file list exists, for example because the evidence database is locked, like a missing file list: it searches only the open partition, without an error (#97). Chromium Session Restore now also ends with status `partial` and a note when another partition cannot be opened or a session file cannot be copied (before: `ok`), and with `cancelled` when it is cancelled between two partitions (before: `ok`). An embedded Chromium root whose path is too long for a file list query (more than 40,000 bytes, for example from an imported file list) is no longer searched through the file list; Chromium Session Restore then ends with `partial` and names the root in a note. Earlier runs of either extractor with seven or more browsers may lack the files of other partitions; for Chromium Session Restore this includes the default selection. Run them again: for Chromium Session Restore use **Run Extraction** and confirm overwriting, because **Run All** and the case-wide run reuse its existing output; Chromium Cache is extracted again by every run (#87).
- Fixed **Firefox HSTS** finding no `SiteSecurityServiceState.txt` in the application. Every run ended with status `skipped` and "No SiteSecurityServiceState.txt files found", on any partition. The extractor now finds the files through the file list on all partitions and reads each file from its own partition, so the recorded partition, file system type and hashes belong to the file that was copied. Firefox HSTS needs a file list and does not scan the filesystem: without a file list the run stops with an error that asks you to run the File List extractor first, and a file list without the file ends with `skipped`. For an E01 image the file list is normally created when the evidence is added; directory evidence needs an imported file list. Evidence where Firefox HSTS ran before this fix still has the empty output of that run: use **Run Extraction** for Firefox HSTS and confirm overwriting, because **Run All** and the case-wide run reuse existing output and do not extract again. A run that stopped with an error or was cancelled is not reused; the next run extracts again. Files on a partition that cannot be opened are skipped and not read from another partition: the run ends with status `partial`, `manifest.json` lists them under `skipped_files`, and a note is written to `manifest.json` and the evidence log. File list rows without a partition number (for example from an imported CSV without a partition column) are looked up on the open partition only and recorded with that partition; on an image with partitions, `manifest.json` and the evidence log say so in a note. A failed file list query now stops the run with an error (before: `skipped`). A file that cannot be copied, or that is larger than 16 MiB, gives status `partial` with a note in `manifest.json` (before, a failed copy ended with `ok` without a note). Files in a Firefox ESR profile are now labelled `firefox_esr`, as in Firefox History and Cookies. Errors in **Ingest Results** for Firefox HSTS are fixed with it; none could be reached before, because no file was ever extracted. Ingestion failed with a `TypeError` before reading the first file and with a second error before saving. The HSTS state was read wrongly: active entries (state 1) were stored with mode `knockout`; states now follow Firefox (0 `unset`, 1 `force-https`, 2 `knockout`, 3 `negative`). Ingesting the same run again did not remove its earlier HSTS rows. URL records from HSTS now name the partition in their notes (#89).
- Removed the **Scan all partitions** option from the configuration of the 51 extractors that had it. Looking for files on all partitions through the file list is no longer optional. "The open partition" below is the one SurfSifter selects automatically when it opens the image (normally the largest one with a Windows folder). 21 extractors applied the option and can no longer be limited to the open partition: Chromium Autofill & Credentials, Bookmarks, Browser Config, Cookies, Downloads, Extensions, Favicons & Top Sites, History, Media History, Site Permissions, Session Restore, Site Engagement and Sync Data; Firefox Autofill & Credentials, Browser Config, Cookies, Downloads, Extensions, History and Site Permissions; Tor State. With the option checked (the default), they behave as before. Output of these 21 from an earlier run with the option unchecked (evidence log: `'scan_all_partitions': False`) covers only the open partition. To cover the others, use **Run Extraction** for that extractor and confirm overwriting; **Run All** and the case-wide run reuse existing output and do not extract again. 30 extractors showed the option but ignored it: all IE / Edge Legacy and Safari extractors with the option, Firefox Bookmarks, Cache, Favicons, Session Restore, Sync Data, HSTS and Browser Storage, and Chromium Cache, HSTS and Browser Storage. Their behaviour is unchanged, but for 26 of them the evidence log recorded `'scan_all_partitions': False` after unchecking it. The run configuration in the evidence log no longer contains the setting. The 20 extractors whose only option it was (9 IE / Edge Legacy, 11 Safari) now report "no configuration options" on **Configure**. Files on other partitions are found through the file list. Without a file list, many of the 51 find nothing (for example Chromium Cookies and Chromium Bookmarks) and the rest search only the open partition. Before, unchecking the option made the 21 search the open partition without a file list; now run the File List extractor first. This change does not fix existing problems with other partitions in Chromium Session Restore (fixed separately, see #87), Chromium Cache (the part with many browsers is fixed separately, see #87), Firefox HSTS (fixed separately, see #89), Tor State, Firefox Site Permissions, Firefox Browser Storage, Firefox Session Restore, Chromium Browser Storage and Firefox Cache, which are the same as before with the option checked; the wiki lists them under Workflow and Behavior → Partitions. Extractors that never had the option are not changed; Registry Reader, DPAPI Decrypt and macOS Plist Reader search only the open partition (#78).
- SurfSifter now fits small screens: 1366×768, and 1280×720 logical pixels (1080p at 150% scaling). Before, the window could not be made lower than about 1,170 px while a case was open, because the **Reports** tab forced its height on every tab; the buttons at the bottom were off-screen on smaller screens. The minimum is now 544 px (measured with a 9 pt font). The **Case**, **Overview** and **Reports** tabs scroll where they do not fit and look as before where they do. In Reports, **Report Settings**, **Custom Sections** and **Appendix** scroll together, and the Preview and PDF buttons always stay visible below them; a long section title no longer pushes buttons out of view. Dialogs fit too: their content scrolls or shrinks, their buttons stay visible, and they do not open larger than the screen. This includes **Preferences**, the extractor configuration and all record details, where long values scroll sideways instead of making the dialog wider than the screen. Message boxes with a long list, such as **Similar Images**, are not covered. Where these tabs and dialogs scroll, the mouse wheel no longer changes a combo box, spin box or date field; it scrolls instead. The window is restored on the screen where it was closed, or on the primary screen if that screen is missing, and its title bar stays on the screen (#77).
- Fixed an error when saving **Preferences** while a case with evidence is open. The settings were saved, but a changed **Thumbnail size** did not reach the Grid of open Images tabs and the log line `Preferences updated` was not written. The new size now applies to the Images Grid of every open evidence. As before, thumbnails that are already cached are not regenerated at the new size (#75).
- Fixed **Configure** (Extractors tab) and **Configure Selected…** (case-wide dialog) failing with an error for nine IE and Edge Legacy extractors: IE Classic History (History.IE5), IE/Edge DOM Storage, Legacy Edge Container, IE/Edge Favorites, IE/Edge File Cookies, Edge Legacy Reading List, IE/Edge Tab Recovery, IE Typed URLs and IE/Edge WebCache. Their only option was **Scan all partitions**, which is removed (#78), so **Configure** now reports that they have no configuration options. These extractors search all partitions in the file list, as before (#76).

## v0.4.0-beta - 2026-10-27

- Images tab (Grid and Table): new **URL exclude** and **Cache Key exclude** fields next to **URL** and **Cache Key** hide images with any discovery whose cache URL or cache key contains a text, for example `favicon`. Images without a URL or cache key (carved or filesystem images) are kept, so URL `X` and URL exclude `X` together show every image exactly once. Include and Exclude combine: URL `cdn` with URL exclude `favicon`. Like the include fields, they apply 400 ms after you stop typing and are cleared by **↻ Reset**. All four fields now match literally: ASCII letter case is ignored and `%`, `_` and `\` are ordinary characters. Before, `%` and `_` in URL and Cache Key acted as wildcards. The Tags dropdown has a new **Untagged** entry after **All tags** that shows only images without a tag of the evidence; a tag that is itself named `Untagged` is listed separately and works as before. After tagging, the Table view now reloads too, so tagged images leave it while Untagged is selected. Fixed the Table view keeping the previous size filter after choosing **All sizes** or **↻ Reset**. On 100,000 images with 3 discoveries each, the first page takes 0.86–1.0 s with an Exclude field, about 0.84 s with Untagged and about 1.0 s with both, compared with 0.8 s without a filter; most of that time is spent building the per-image source summary for all images, before the filters apply. Measured with the opt-in benchmark `tests/app/test_images_filter_benchmark.py` (#74).
- File List tab: a new **Exclude** field next to Search hides files whose name or path contains a text, for example `WinSxS`. It matches like Search, and both now match literally. ASCII letter case is ignored, `%`, `_` and `\` are no longer wildcards, and leading and trailing spaces are ignored. Before, `%` and `_` in Search acted as wildcards. Exclude is applied with Enter or Search, and Search and Exclude combine: Search `.dll` with Exclude `WinSxS` shows DLLs outside `WinSxS`. The Tags dropdown has a new **Untagged** entry after **Any Tag**, which shows only files whose Tags cell is empty. **Any Tag** now counts only tags of the evidence, so Any Tag and Untagged together always cover all files. Before, Any Tag also showed files linked only to a deleted tag. A tag that is itself named `Untagged` or `any` is listed separately and filters as a normal tag; before, a tag named `any` could not be selected on its own. The Extension, Matches and Tags dropdowns keep their selection when their lists reload, for example after tagging, and while a list is loading or failed to load the selected filter stays applied. The Tags column of tabs that use the shared tag lookup (File List, URLs, Browser Inventory, OS Artifacts, image tags) now shows only tags of the evidence, which only matters for an association to another evidence's tag. On 1 million files without planner statistics, a filter change blocks the window for about 0.45–0.7 s with Search or Exclude, compared with 0.3 s without a filter. With Untagged or Any Tag it takes 1.1–1.3 s, about 1.5 s combined with Exclude, and up to about 2.6 s when 99% of files are tagged. Measured with the opt-in benchmark `tests/app/test_file_list_query_benchmark.py` (#73).
- URLs tab: a new **Exclude** field next to Search hides URLs that contain a text, for example `google`. It matches like Search: ASCII letter case is ignored, `%`, `_` and `\` are literal characters, and it is applied with Enter or Search. Search and Exclude combine (contains `login` but not `google`). The Tag dropdown has a new **Untagged** entry after **All tags** that shows only URLs whose Tags cell is empty; a tag that is itself named `Untagged` is listed separately and works as before. Both filters apply to the table, the grouped view, the totals and CSV export, and combine with all other filters. Exclude never uses the search index. On 1 million URLs, the first page with Exclude takes 3–7 ms, or about 0.4 s when the text is in every URL (nothing left to show); Search plus Exclude with the search index takes about 35 ms. With Untagged, the first page takes about 3 ms when few URLs are tagged and about 0.35 s when 99% are tagged; the total is counted in the background in 0.5–1.4 s. Measured with the opt-in benchmark `tests/app/test_url_query_benchmark.py` (#72).
- Browser Inventory → History: the **Browser** and **Profile** dropdowns now update after **Ingest Results**. Before, they kept the browsers and profiles from the first time History was opened, so a new browser or profile could not be selected without reopening the case. A reload after ingestion now also applies the filters shown above the table (Browser, Profile, Type and URL text, including URL text typed without clicking **Apply**). Before, it showed every row while the controls still showed the old filter. A selected browser or profile that no longer exists falls back to **All**. As before, History reloads right away if it is open when ingestion finishes, and otherwise the next time you open it (#69).
- OS Artifacts: new results now appear after **Ingest Results** (or after extraction, for extractors without a separate ingestion step) without restarting SurfSifter. Before, the tab could keep showing empty or old rows when you returned to an evidence added during the session that had OS Artifacts already selected, and new indicator types and browsers were missing from the dropdowns. Registry Findings, Jump Lists, Installed Applications, Application Execution and User Activity now reload their rows and summaries together, and also update the **Indicator Type** and **Browser** dropdowns. A selected filter that still exists stays applied; one whose rows are gone falls back to **All**. The embedded DPAPI subtab refreshes when shown. Evidences that are not shown are not reloaded until you open them. If loading fails, the tab tries again the next time it is shown (#68).
- Opening a case no longer checks the external tools' versions for every evidence. Before, each evidence tab started about 56 `--version` subprocesses on the GUI thread (about 1.2 s per evidence). Each tool's version is now checked once per session, and checked again when its path or executable changes, or after **Refresh All**, **Set Custom Path** or **Reset to Auto** in **Preferences → Tools**. Foremost and Scalpel image-carving runs (Media extractors) still check the version again before they start, so the run manifest records the version that ran. With 20,000 URLs per evidence, the window is blocked while opening the case for 0.4 / 1.4 / 2.1 s instead of 1.6 / 6.2 / 12.3 s (1 / 4 / 8 evidences). Measured with the opt-in benchmark `tests/gui/app/test_case_open_benchmark.py` (#70).
- URLs tab: the grouped view (**Group by domain**) now covers every matching URL instead of only the first 10,000, and no longer blocks the window. Domains are listed alphabetically, 500 at a time, with exact URL counts. Domains that differ only in letter case form one group, like the Domain dropdown, and URLs without a domain are grouped under **(no domain)** at the end. A domain's URLs load in the background only when you expand it, 500 at a time and in the table's order. **Load more…** rows load the next domains or URLs, and a failed load can be retried from its row. Expanded domains stay expanded after a refresh or tagging. Loaded URLs of collapsed domains are kept up to 5,000 URLs. With 1 million URLs, the first domains appear after 0.1–0.3 s and an expanded domain's first URLs after about 50 ms, with the window blocked for at most 40 ms. Before, the window was blocked for 1.4–2.3 s and only the first 10,000 URLs could be reached. Measured with 5 and about 100,000 domains (2% of URLs without a domain) using the opt-in benchmark `tests/gui/app/test_urls_grouped_benchmark.py` (#64).
- Cases with several evidences open much faster and stay responsive. Evidences you have not shown yet no longer read data, count anything or start background work: each sub-tab (Download counts, Browser Inventory, File List, Extractors status, Tags, Reports, Screenshots, Audit) loads the first time it is shown. With 1 million URLs per evidence, the window is blocked while opening the case for 1.5 / 6.1 / 12.1 s instead of 4.9 / 26.2 / 72.3 s (1 / 4 / 8 evidences), and background work after opening ends after 1.6 / 6.3 / 12.8 s instead of 16 s / 3.9 min / more than 10 min, using 0.6 / 1.9 / 3.9 instead of 18 / 749 / 4,017 CPU seconds; memory after opening 8 evidences is 488 MB instead of 1,004 MB. The Overview counts load in the background while the Overview is shown (`Loading…`, `—` on error) and are remembered per evidence until something changes them, so switching back to an evidence shows them at once. The URLs tab shows its first rows without waiting for the filter dropdowns (about 50 ms instead of 0.4–0.7 s); the dropdowns load in the background, keep your selection when they reload, and are reloaded after ingestion, tagging, deduplication and list matching. Opening another case or closing an evidence tab stops the background work of all its sub-tabs. Measured with the opt-in benchmark `tests/gui/app/test_case_open_benchmark.py` (#63).
- URLs tab: text search for rare text is much faster on large evidence. For rare or absent text, the total and first page now take milliseconds instead of about 0.15–0.3 s and 0.4–0.65 s on 1 million URLs, and instead of about 2–3.5 s and 4–10 s on 10 million URLs. A search index (SQLite FTS5 trigram) is built in the background the first time the URLs tab is shown for an evidence, and again for new URLs after ingestion. A status next to the Search button shows its progress. Search results, their order and totals are unchanged: URLs not indexed yet, one- and two-character searches, and common text are searched without the index. The build pauses when you leave the URLs tab and while a case export runs. When a build that indexed URLs finishes, the shown table page is reloaded and the total recounted (beyond page 1, row numbers are then hidden until you return to page 1). Case export waits for running builds to stop, and is not started if one is still finishing. If SQLite lacks FTS5 trigram support, search works as before. Evidence migration 0006 adds the index state. The index takes about 50–110 MB per million URLs, depending on URL length; building it takes about 10–40 s per million URLs on 1 million URLs and about 13 minutes for 10 million. Adding URLs costs nothing extra; deleting already-indexed URLs (re-extraction cleanup, deduplication, purge) is about 1.5–1.8 times slower on 1 million URLs and about 3.4 times slower on 10 million. Each build session that indexes URLs is recorded in the evidence process log; it does not change the evidence's "Last Extraction" time. Deleting URLs by run or by evidence now reports only deleted rows (#62).
- URLs tab: filtering by a single source is fast again for sources whose URLs have no First Seen time (e.g. carved URLs). Evidence migration 0005 extends the source index with First Seen. The index is rebuilt once when an existing case is opened. The domain dropdown now lists domains that differ only in letter case (`Example.COM`, `example.com`) as one entry, whose count matches the URLs it shows. Domains with equal counts appear in a fixed order. When you return to the URLs tab after changing tags in the Tags tab (rename or merge), the total is recounted without having to change pages (#67).
- URLs tab: fixed editing an **Occurrences** cell, which replaced the URL's tags with the typed value. Occurrences is now read-only, and the **Tags** cell is the editable column again. An inline tag edit recounts tag-filtered totals. The grouped view now shows each URL's existing tags, so editing them no longer starts from an empty cell and drops tags. Inline tag edits no longer remove a tag when only its letter case changes, and no longer split tag names that contain a comma. The tag filter now matches the selected tag exactly (ignoring case), and the URL text search matches `%`, `_` and `\` literally instead of as wildcards (#66).
- URLs tab: the first rows no longer wait for the total count. The exact total loads separately; the counter shows it as pending (`of … URLs (counting)`) until it is known. It is cached per filter, so Previous/Next does not count again. Paging uses a stable cursor order: First Seen newest first, URLs without a timestamp last, ties by ID. Pages are smaller and selectable (default 500 rows, remembered). The domain dropdown is now an exact, case-insensitive match, and a new "Domain contains" field provides literal substring search. Evidence migration 0004 adds an index for exact-domain browsing. CSV export reads rows in cursor batches; its output is unchanged (#61).
- URLs tab: the flat view's initial load, filter changes, Previous/Next and refresh now run in a cancellable background worker. Stale requests are interrupted inside SQLite and their results are discarded. Untagged URLs no longer trigger per-row tag lookups, and refresh reloads only the visible view (#60).
- Add a first-class Firefox Browser Config extractor for curated `prefs.js` and `user.js` settings with source-distinct ingestion into `browser_config` (#58).
- Add a first-class Chromium Browser Config extractor for curated `Preferences` and `Local State` settings (#57).
	- Note: older case workspaces ingested with the previous Chromium Extensions side-effect may still contain those historical `browser_config` rows until the case is intentionally cleaned or reprocessed.
- Add a read-only Browser Config subtab to Browser Inventory for filtering and inspecting stored `browser_config` evidence rows (#56).
- Fixed Chromium Media History playback parsing when SQLite rows are read via `sqlite3.Row`, including databases with `playback.origin_id` joined to the `origin` table (#31).
- Add app_execution, browser_history and installed_software to tagged summary export.
- Route Tag Summary `download`/`downloads` tags to the investigator downloads table as **Downloaded files**, distinct from browser download artifacts.
- Add embedded thumbnails for tagged images and image reference-list/hash matches in Tag Summary XLSX exports.
- Harden report and appendix image thumbnails: sources must resolve under the selected evidence workspace, generated thumbnails are embedded inline in report output, stale cache files are not trusted as report-visible evidence, and Pillow/optional pillow-heif rendering uses the shared thumbnail safety limits.
- Harden image/download/screenshot report HTML rendering by enabling Jinja autoescaping for evidence-derived fields.

## v0.3.8-beta - 2026-05-07

- Added batch folder import for URL reference lists with shared metadata and conflict handling.
- Removed the unused SQLite Hash DB preferences and rebuild workflow while keeping text hash-list matching.
- Removed deprecated YAML Rules preferences and internal rules_dir plumbing.
- Fixed `NameError: name 'normalized_logical_path' is not defined` in `chromium_sessions` extractor's `_collect_url_data()`, which caused all session files to be marked `error` in `browser_cache_inventory` and silently skipped URL cross-posting to the `urls` table (#55).
